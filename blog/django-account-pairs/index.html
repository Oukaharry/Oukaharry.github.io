Pairing live and prop-firm accounts in Django

By Harrison Odhiambo Ouka · 8 November 2026 · 4 min read

HedgePass Pro is a Django project I published for prop-firm challenge hedging and trade management. The public app has a landing page, signup and login, a client area, account management, performance pages, and settings. A demo is at hedgepass-pro.vercel.app, and the source is at github.com/Oukaharry/hedgepass-pro. I am a software developer writing about the data model. This is not a trading strategy. The repository says the software does not manage accounts and does not give trading advice.

A pair is the unit of work

The app is aimed at two accounts that have to be thought about together: a live account and a prop-firm account. Both AccountPair and MT5Account carry an account type of LIVE or PROP, an account number, a server name, a pair number, an active flag, a timestamp, and a foreign key to the user. The unique constraint is (user, account_type, pair_number). Pair 1 can hold one live row and one prop row for the same person. A second live row with the same pair number is a database error, not a display bug you find later.

unique_together holds the rule because views forget. Filtering on is_active lets you retire a pair without deleting it. The user model is a thin AbstractUser with is_premium and an mt5_license field added to Django's username and email.

AUTH_USER_MODEL is set to main.User. In settings.py it is assigned twice: first to auth.User, then to main.User. The later line wins. A custom user has to be decided before the first migration, because swapping it afterwards means rebuilding the database. I would delete the early assignment so the setting cannot drift.

class AccountPair(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    account_type = models.CharField(max_length=4, choices=ACCOUNT_TYPES)
    pair_number = models.IntegerField(default=1)

    class Meta:
        unique_together = ("user", "account_type", "pair_number")

Passwords at rest

Account numbers are not particularly secret. The trading password is. The form uses PasswordInput, and the model encrypts the value with Fernet, from the cryptography library, inside save before the row hits SQLite. Fernet needs a key. The project already reads the Django secret key from the environment. The encryption key belongs there too, not in the repository.

Reversible encryption is not hashing. Hash a password when you never need the original; a broker password has to be presented later, so Fernet fits and a one-way hash does not. Encrypt on every write. AccountPair.save only encrypts when pk is missing, so a later edit can store plaintext, while MT5Account.save tries to cover updates. Use one helper for both. Skip values that are already Fernet tokens, or a resave double-encrypts them. Keep the password out of logs, the admin list, and templates.

The installed apps also include django_cryptography beside the manual Fernet calls. One approach is enough. Two ways to encrypt the same column is how a row becomes unreadable after a deploy.

The pages follow the login

urls.py splits the site into a public landing page and views wrapped in login_required: add an account, list pairs, the client area, account management, performance, portfolio performance, and settings. Login redirects to the client area. Logout returns to the landing page. WhiteNoise serves static files. Templates live under main/templates/main, and the front end in the repository is HTML, CSS, and JavaScript. The development database is SQLite.

The landing route is registered twice under the same name. Django uses the last stored name when you reverse a URL, and the first pattern when it matches a request. It works until someone reorders the list. One path, one name.

The performance view is the seam I would close next. It looks up AccountPair with both the id and request.user, which is the right check. The URL that points at it does not pass a pair_id, while the view requires one. The view also fills the template with placeholder profit and win-rate numbers, marked in the source as figures to replace. Those figures are not account results. I would not ship the view until the path and the function agree, and I would keep the user filter on every query added along the way.

The README's local setup is a virtual environment, dependencies, migrate, and runserver. Its activate line uses the Windows Scripts path; on Linux or macOS the script is in bin.

What not to commit

The public tree contains a development db.sqlite3, compiled __pycache__ files, and an environment file. None of those belong in git. Bytecode is specific to a Python version. A SQLite file can hold user rows and encrypted passwords. An environment file is where the secret key and the Fernet key live. Ignore __pycache__/, db.sqlite3, and .env in the first commit, not the cleanup commit.

Deleting them later is not enough if they were pushed. History still has the blob. Rotate the keys and treat the old database as exposed. Encryption does not help once the key shipped beside the ciphertext. I am not pasting that environment file here. The lesson is that the file is in the tree.

A small shape that can grow

The model is a user, a pair number, two account types, and a password encrypted before it rests. Keep order execution behind a boundary that receives an account id, decrypts on the server, and never returns the password to the browser. The client area can stay a view that lists pairs the logged-in user owns.

That is the part I would carry forward: a pair as a database constraint, secrets outside the repository, and every account query scoped to the logged-in user. TradeManagerEA does the chart side of the same work. They meet at an account number that should never be logged next to a password.

Trading can lose money. This article is about the Django project as published. The placeholder figures in the performance view are not results, and nothing here is trading advice.
